# Instamart Customer Intelligence & Support Copilot

## Overview

An internal Customer Intelligence & Support Copilot for Swiggy Instamart, built as one reproducible Python repository across four connected parts: a clean SQLite data foundation (Part A), customer segmentation and lapse prediction (Part B), privacy-safe support-ticket triage (Part C), and a policy RAG assistant plus refund agent (Part D). All data is synthetic and generated by the supplied `generate_data.py`; all model calls use the supplied offline `mock_llm.py`. Monetary values are in INR.

Build plan: `PLAN.md`. Progress tracker: `TRACKER.md`. Agent operating rules: `AGENTS.md`. Full extracted brief: `docs/ASSIGNMENT_BRIEF.md`.

**Status:** final local deliverable ready. Folder/repository name: `instamart-customer-intelligence-support-copilot`. Clean-copy run of every README command passes all checkpoints; public repository publication and final commit/push remain pending explicit approval.

We chose K=4. The elbow is clear between K=3 and K=4, and K=4 has the highest silhouette score (0.526) as well as four profiles the business can act on. ### Lapse cohort and baseline

The cohort contains 1,156 customers with a completed order strictly before 2025-09-01. Of these, 443 lapsed (38.32%). The stratified split produced 924 training rows and 232 test rows. Always predicting "not lapsed" gives 61.6% accuracy and a lapsed-class F1 of 0.

### Preprocessing and tuning

The logistic pipeline's scaler learned a mean frequency of 8.115 from the training rows, while the full-cohort mean is 8.029; they differ because the scaler is fitted on the 924-row training split only. No feature column contains a missing value. All encoders, scalers and the resampler were fitted on training rows only and merely applied to the untouched test rows; no feature uses an order dated on or after the cutoff, and the Part B segment labels were not used as features.

| Model | Best parameters | Best CV F1 | Confusion matrix | Precision (lapsed) | Recall (lapsed) | Test F1 (lapsed) |
|---|---|---|---|---|---|---|
| Logistic regression | C=100 | 0.651 | TN 111, FP 32; FN 31, TP 58 | 0.644 | 0.652 | 0.648 |
| Random forest | max_depth=8, min_samples_leaf=10 | 0.681 | TN 113, FP 30; FN 31, TP 58 | 0.659 | 0.652 | 0.655 |

We selected the random forest because it has the higher test F1 (0.655 versus 0.648) and a slightly better precision at essentially the same recall. The decision weighs the cost of missing a lapsing customer, which loses future revenue and is hard to recover, against the cost of wrongly targeting a loyal customer, which is only a small incentive. The selected model clears the required test F1 of 0.55.

### Class-balance experiment

| Model | Precision | Recall | F1 |
|---|---|---|---|
| Unbalanced | 0.644 | 0.652 | 0.648 |
| Oversampled | 0.589 | 0.854 | 0.697 |

Recall moved most, rising from 0.652 to 0.854, while precision fell slightly from 0.644 to 0.589. The retention team catches many more customers who are about to lapse, but it also targets more loyal customers with unnecessary incentives.

### Interpretation, persistence and retention list

The five most important random-forest features are frequency (0.280), monetary (0.271), recency (0.115), average delivery minutes (0.061) and cancellation rate (0.052). Three logistic coefficients are: recency +0.0396, so a longer gap since the last order raises lapse odds; frequency -1.6982, so more completed orders lower lapse odds; and monetary +0.2846, so higher spend raises lapse odds slightly once frequency is held fixed, likely reflecting large electronics buyers rather than a causal effect. The saved model reloaded from `outputs/lapse_model.joblib` reproduces the original test predictions exactly. The top ten Premium test customers by predicted lapse probability contain 1 customer who truly lapsed; the list is written to `outputs/retention_list.csv`.

The Premium flag comes from the whole-window RFM of task 3, which includes the September window that defines the lapse label, so it is a post-hoc whole-window label. The retention list is therefore illustrative and not a leakage-free evaluation; the model's own features still use only orders before the cutoff.

For `refund policy late delivery`, the top three retrieved chunks all come from `refund_policy.txt` (scores 0.272, 0.251 and 0.245). TF measures how often a term occurs inside a chunk and therefore its local importance; IDF measures how rare the term is across all chunks and down-weights common words. A limitation is that TF-IDF is lexical: two questions with the same meaning but different wording share few terms and can retrieve the wrong chunk.

`answer(question)` sends exactly two messages: a system prompt containing `POLICY ASSISTANT`, and one user message with `CONTEXT:` followed by the top-three source-labelled chunks and `QUESTION:` followed by the question. It returns the model's grounded text plus the list of source filenames. When the context lacks the answer, the assistant replies that it could not find the information in the policy documents.

### ReAct versus plan-and-execute

ReAct interleaves one model call with one tool action. On the measured runs S1 needed 5 calls and 1,132 tokens, S5 needed 3 calls and 478 tokens, and S6 needed 2 calls and 166 tokens. A plan-and-execute design would ask for the whole step list once, which could use fewer calls and tokens when the path is predictable. However, unexpected observations are common here: S6 gets a not-found order and must stop immediately, while S5 gets a cancelled order and must deny without calculating a refund. ReAct handles both naturally; plan-and-execute would need to replan (extra calls) or risk following a stale plan. For this short, branching refund workflow I would choose ReAct because correct denial, escalation and human handoff matter more than saving a few calls, and the measured token cost is small. Plan-and-execute is a better fit for long, deterministic workflows with many routine steps and few surprises.

## Limitations and Next Steps

- The Premium flag used by the retention list is a post-hoc whole-window label: the Part B segmentation includes the September window that defines the lapse target. The retention list is therefore illustrative and not a leakage-free evaluation. The lapse model's own features still use only orders before the 2025-09-01 cutoff.
- All data is synthetic and fictional, and every model call uses the deterministic offline `mock_llm.py`; real customer language and real model behaviour may differ.
- TF-IDF retrieval is lexical and can miss paraphrases or answers split across chunk boundaries; the zero-overlap evaluation demonstrates this failure mode.
- The refund agent treats every request as inside the 7-day policy window and uses a fixed 45-minute refund rule; production rules, exceptions and manual approvals would be richer.
- The system has no production monitoring, alerting, model calibration or privacy review beyond the regex redaction demonstrated here.
- Next steps: integrate a real ticketing system and order service, calibrate lapse probabilities and choose campaign thresholds against retention economics, monitor data and model drift, add human-in-the-loop review dashboards, and strengthen PII detection beyond email, phone and order ID patterns.
